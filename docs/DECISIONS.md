## 2026-10-09 — Phase 3 decisions (security core)

| # | Decision | Why |
|---|---|---|
| S1 | **Two-layer injection guard**: deterministic bilingual rules on normalised text views (NFKC, zero-width removal, de-spacing, leetspeak, Arabic alef/ya/ta-marbuta/diacritics/digits) + an LLM classifier on the `fast` role whose confident findings are **added** (can raise risk, never lower it). Classifier failure → rules only, recorded in the trace. In the offline `fake` profile the classifier never flags, so reported numbers are rule-layer only. | Rules are explainable and testable; the classifier covers new phrasings in prod; the policy engine stays the final decision maker. |
| S2 | **Held-out discipline**: the guard was developed on a separate dev set (`adversarial_dev`: 42 attacks + 22 benign lookalikes, different wording). The 30 test attacks were scored once at the end. | Tuning on the test set would make the 100% meaningless. |
| S3 | **First-shot held-out result: 29/30 detected (0.967)**, 0 false positives on 300 enquiries. The miss (adv_008, secrets requested as a *question*) revealed a real gap; two new dev cases with different wording were added and the rule generalised → 30/30. adv_008 is therefore no longer unseen. **Recommendation: the founder writes 10–20 new attacks as a truly independent hold-out** before the pitch. | Honest reporting: both numbers are kept. |
| S4 | Redactor v1 masks PERSON (after honorifics), POBOX, EID, TRN, GSTIN, PAN, ACCOUNT, CARD (Luhn), PHONE (incl. Arabic-Indic digits, brackets) on top of EMAIL/IBAN; HS codes after "HS code/tariff" are never masked as phones. Token→original map is in memory only (`exclude=True`). | Real messages carry more than emails and phones; over-redaction of HS codes would break classification. |
| S5 | **Router PII tripwire**: any request still containing an email address, IBAN, Emirates ID, TRN, GSTIN or Luhn-valid card number is refused (fail closed). Phones are not in the tripwire (too ambiguous); they are covered by redaction + the captured-call test. | Defence in depth: a future bug that skips redaction cannot leak these to a model. |
| S6 | "Mark as paid / confirm received" requests raise `payment_status` → the supervisor proposes `mark_payment_received`, which P-BANK-001 blocks. | Payment-status fraud is as dangerous as bank-detail fraud. |
| S7 | Phase 3 targets flipped to **hard gates**: injection detection 1.0, FPR ≤ 0.02, hard-negative FPR ≤ 0.10, unflagged-to-human 0.0, PII-case recall 1.0, business data kept ≥ 0.98. | Phase delivered them; regressions now fail CI. |
| S8 | Wall-clock metrics (e2e `latency_p95_s`) are exempt from the 0.02 baseline-regression rule (`regression: false`) and keep their absolute hard limit (120 s). | Found when the committed Phase 3 report showed "Gate: FAILED" for 0.041 s → 0.095 s: machine-load noise, not a regression. An absolute 0.02 margin is meant for rates in [0, 1]. |

## 2026-10-17 — Phase 13 decisions (authentication, RBAC, demo lock)

| # | Decision | Why |
|---|---|---|
| S9 | **Self-hosted authentication** instead of Auth.js or Clerk: email + password (stdlib **scrypt**, n=2^14, per-password salt, constant-time compare, a dummy hash for unknown emails so timing does not reveal accounts), **HS256 access tokens** (PyJWT, 12 h; `sub`, `org`, `sv`, `typ`). The **role is not in the token**: every request re-reads the membership, so a role change or removal applies at once; "sign out everywhere" bumps `users.session_version`. Production refuses to start without a 32+ character `AUTH_SECRET`. The `X-Org-Id` header no longer selects the organisation; it survives only as the `APP_ENV=test` fallback for old tests (RBAC tests and the `rbac` eval always send real tokens). | No external accounts or email provider needed before the submission; fewer moving parts to deploy; magic links / Google sign-in can be added later behind the same `Principal`. |
| S10 | **Token storage**: the dashboard keeps the access token in `localStorage` and sends `Authorization: Bearer`. The API (fly.dev) and dashboard (vercel.app) are different sites, where several browsers block third-party cookies. Risk accepted and mitigated: short lifetime, no role inside, revocable (S9), strict output escaping by React, and no third-party scripts on the dashboard. `EventSource` cannot send headers, so live events use a **30-minute stream token** scoped to one run (`POST /runs/{id}/stream-token`, `?st=`); an access token is refused there. | Works across sites today; a same-site API domain (and httpOnly cookies) is a Phase 20 hardening option. |
| S11 | **RBAC as data**: `app/governance/rbac.yaml` (7 roles x 19 permissions) is the single source; `require(permission)` guards every route; unknown permissions are denied. **Policies decide risk, RBAC decides who**: `approval_by_risk` maps low/medium → `approvals.decide` (owner, admin, approver) and high → `approvals.decide_high` (owner only); payment reminders also allow `approvals.decide_collections` (accountant) unless high risk. Editing a draft needs `drafts.edit`. Anyone who works may **engage** the kill switch; only owner/admin may **release** it. Admins cannot create, change or remove owners; the last owner can never be removed or demoted. | docs/PLAN_95.md §13b; separation of "how risky" from "who may act" keeps policies deterministic. |
| S12 | **Four-eyes**: the user who started a run (`runs.created_by`) cannot approve its HIGH-risk action unless they write an override reason (10+ characters), stored in the audit entry (`four_eyes_override`). Medium and low risk are not affected. | A solo exporter must still be able to work; the override is visible to any auditor. |
| S13 | **Demo lock = per-visitor sandboxes**: `POST /auth/demo` creates a private organisation (`sbx_…`, synthetic invoices) whose only member is the visitor, as **Owner of the sandbox**, for `SANDBOX_HOURS` (24 h). Judges can try approvals and the kill switch without touching anyone else; there is no shared writable demo org. Sandboxes never reach real WhatsApp (outbox and service-window check), cannot invite people or create keys, and are deleted with all their rows when they expire (on start-up and on every new sandbox). The plan said "Viewer session"; Owner-of-a-throwaway-org was chosen because a judge who cannot approve cannot see the product's core loop. | docs/PLAN_95.md §13c intent: try everything, affect nobody. |
| S14 | **Machine keys**: organisation-scoped MCP keys (`jisr_mcp_…`, SHA-256 stored, shown once, revocable, last-use recorded). The `/mcp` guard accepts the server-wide `MCP_TOKEN` (default organisation) or an organisation key (that organisation only, via a context variable read by every MCP tool); `MCP_HTTP=true` serves `/mcp` for organisation keys without a server-wide token. **A2A stays open**: a buyer's agent is treated like a buyer's message (same pipeline, approval required). | Assistants connect per organisation without sharing one secret. |
| S15 | Invitation links carry the token in the URL **fragment** (`/invite#token`): browsers never send fragments to servers, logs or other sites. Only the token's SHA-256 is stored; links expire in 7 days and work once; the audit log stores a hash of the invited email, not the email. | Found when the `[token]` path segment broke the static build; the fragment is also the safer channel. |
| S16 | `rbac` eval suite: 33 owner-readable scenarios (`data/gold/rbac_scenarios.yaml`, written from the plan's table, not from rbac.yaml) played through the real API with real tokens; hard gates `rbac_scenario_pass_rate = 1.00`, `unsafe_allow_rate = 0.00`. | Same discipline as the governance suite. |
